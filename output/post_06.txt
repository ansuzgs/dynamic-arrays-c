  Demo 4: Three error handling strategies compared
═══════════════════════════════════════════════════════════

  Strategy A: Return Codes (what we use)
  ─────────────────────────────────────────
  ArrayError err = array_push(arr, &val);
  if (err != ARRAY_OK) {
      fprintf(stderr, "push failed: %s\n",
              array_error_str(err));
      // handle error: retry, degrade, abort
  }

  Pros: explicit, caller decides how to react,
        no hidden control flow, debugger-friendly.
  Cons: verbose (every call needs an if-check),
        easy to forget checking (ignoring the return).

  ───────────────────────────────────────────
  Strategy B: Callback (our optional addition)
  ─────────────────────────────────────────────
  array_set_error_callback(my_handler);
  array_push(arr, &val);  // handler called on error

  Pros: centralized logging, no code at each call site,
        good for metrics and monitoring.
  Cons: doesn't replace return-code checking,
        global state (callback pointer),
        complex if handler needs context.

  ───────────────────────────────────────────
  Strategy C: Abort (not recommended)
  ─────────────────────────────────────────
  void array_push_or_die(Array *arr, const void *elem) {
      if (array_push(arr, elem) != ARRAY_OK) {
          fprintf(stderr, "FATAL: push failed\n");
          abort();
      }
  }

  Pros: dead simple, no error paths to test,
        fine for quick prototypes and scripts.
  Cons: no recovery possible, unsuitable for libraries,
        crashes the entire program on ANY allocation failure,
        makes the library hostile to embedders.

  ═══════════════════════════════════════════
  Our choice: A (return codes) as primary mechanism,
  with B (callback) as optional monitoring layer.
  Never C for library code — let the caller decide.

  Knowledge Test
═══════════════════════════════════════════════════════════

  Q: If realloc fails, what value does arr->data still
     hold? Why must you use a temporary pointer?

  A: arr->data still holds its ORIGINAL value — the
     pointer to the existing, valid buffer with all
     elements intact.

     When realloc fails, it returns NULL but does NOT
     free the original block. The old memory is still
     allocated and usable.

     You must use a temporary pointer because:

       void *tmp = realloc(arr->data, new_size);
       if (!tmp) return ERR;  // arr->data unchanged!
       arr->data = tmp;        // update only on success

     If you wrote:
       arr->data = realloc(arr->data, new_size); // WRONG

     ...and realloc returned NULL, then:
       - arr->data is now NULL
       - The old buffer is still allocated (leaked)
       - All your data is lost AND memory is leaked
       - Double failure: data loss + resource leak

     The temporary pointer costs one extra local variable.
     It prevents data loss. Always use it.
